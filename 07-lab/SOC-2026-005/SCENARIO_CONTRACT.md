# SOC-2026-005 — network traffic investigation scenario contract

## Evidence state

**PLANNED / PENDING EXECUTION**

This document defines the authorized laboratory scenario before the formal evidence
capture. It does not itself demonstrate packet-analysis capability or establish that
the planned observations occurred.

A tooling preflight was completed outside the repository to validate the intended
capture and analysis path. Preflight artifacts are not case evidence.

## Objective

Investigate a bounded network sequence from packet capture through analyst
disposition while preserving a strict distinction between:

- directly observed network facts;
- analyst interpretation;
- alternative explanations;
- laboratory ground truth;
- final disposition.

The case is intended to demonstrate packet-level investigation, connection and HTTP
correlation, file-transfer verification, false-positive control and evidence-aware
SOC reasoning.

## Authorization and isolation

The formal scenario must use only traffic generated by the repository owner in an
authorized local laboratory.

Initial implementation constraints:

- capture interface: macOS loopback `lo0`;
- client address: `127.0.0.1`;
- server address: `127.0.0.1`;
- server port: `18080/TCP`;
- HTTP server: local Python HTTP server;
- capture filter: `tcp port 18080`;
- no external destination is required;
- no credential, personal, customer or production data may be introduced.

Loopback use is deliberate: it provides real endpoint-generated TCP/HTTP traffic
without contacting an external service.

## Planned observable sequence

The formal capture will contain six controlled HTTP GET requests.

### Control A — benign health request

Expected characteristics:

- one HTTP GET;
- URI: `/health.txt`;
- user agent: `Mozilla/5.0 SOC005-Benign-Control`;
- expected HTTP status: `200`.

Purpose:

Provide an explicit benign control that must remain distinguishable from the
repeated lab-agent sequence.

### Sequence B — repeated beacon-like requests

Expected characteristics:

- four HTTP GET requests;
- URI pattern: `/beacon.txt?host=SYN-LAB-005&seq=N`;
- sequence values: `1` through `4`;
- user agent: `SOC005-Lab-Agent/1.0`;
- approximately regular spacing;
- expected HTTP status: `200`.

The term **beacon-like** describes the observable periodic request pattern only.
It does not establish command-and-control activity, malware or malicious intent.

### Sequence C — controlled file retrieval

Expected characteristics:

- one HTTP GET;
- URI: `/lab-update.bin`;
- user agent: `SOC005-Lab-Agent/1.0`;
- expected HTTP status: `200`;
- downloaded bytes must hash identically to the server-side laboratory artifact.

A successful transfer does not establish malware delivery. File content and
provenance must be examined separately.

## Initial analyst perspective

The analyst should begin with network evidence rather than laboratory ground truth.

Observable characteristics that may warrant review include:

- repeated requests with a consistent custom user agent;
- approximately regular request timing;
- a host-like identifier in the query string;
- subsequent file retrieval using the same user agent.

These observations support investigation. They do not independently establish a
compromise.

## Analytical hypotheses

### H1 — malicious beaconing followed by payload retrieval

Potentially consistent observations:

- periodic HTTP requests;
- repeated custom user agent;
- repeated host identifier;
- subsequent binary-named file retrieval.

Evidence required before accepting H1 includes additional context such as artifact
content, destination reputation, process attribution, authorization state or other
corroborating telemetry.

### H2 — authorized controlled-lab automation

Potentially consistent observations:

- loopback-only communication;
- explicit SOC005 markers;
- deterministic sequence values;
- laboratory artifact hash agreement;
- documented scenario authorization.

H2 must not be accepted solely because this scenario document exists. The formal
capture and retained evidence must independently support the relevant observations.

### H3 — benign application health/update behavior

Periodic requests and file retrieval can also occur in legitimate software.

This alternative remains analytically relevant when reviewing network behavior in
isolation. Application identity, authorization, file provenance and endpoint
context are needed to distinguish it from H1.

## Severity model

Before authorization and provenance are correlated, the repeated requests plus file
retrieval may justify **Medium laboratory triage priority**.

This is a bounded exercise severity, not a production incident rating.

Severity must be reassessed after context is collected. The final disposition must
follow retained evidence rather than the scenario's intended outcome.

## Required formal evidence

The case is not complete until retained evidence supports the investigation.

Required evidence targets:

1. formal PCAP captured from the authorized laboratory sequence;
2. PCAP SHA-256;
3. packet and connection counts;
4. `tshark`-derived HTTP request table;
5. Zeek `conn.log`;
6. Zeek `http.log`;
7. Zeek `files.log` when produced;
8. server-side and downloaded-file SHA-256 comparison;
9. formal analyst timeline;
10. findings, hypotheses and disposition;
11. tool versions and capture methodology;
12. explicit limitations.

Suricata analysis may be added as a separate detection layer, but it is not required
to establish the packet-capture observations themselves.

## Zeek checksum handling

The macOS loopback preflight produced a `NULL/Loopback` PCAP for which default Zeek
processing reported `bad_IP_checksum` and did not emit normal connection/HTTP logs.

Reprocessing the same preflight capture with checksum validation disabled using
`zeek -C -r <pcap>` produced connection, HTTP and file-analysis logs.

For the formal capture:

- the condition must be reproduced and documented if it occurs;
- `-C` must be disclosed wherever Zeek-derived evidence is cited;
- ignoring checksum validation must not be represented as repairing or modifying the
  captured packets;
- packet observations should be cross-checked with an independent parser such as
  TShark.

## Evidence boundaries

If the formal capture succeeds, the PCAP and directly derived telemetry may be
classified as **REAL CONTROLLED LAB** evidence.

That classification means the packets were genuinely generated and captured in the
authorized laboratory. It does not mean:

- production SOC experience;
- malicious traffic;
- real command-and-control;
- malware execution;
- customer or enterprise traffic;
- production IDS/IPS operation.

Analyst-authored scenario descriptions, hypotheses and expected outcomes are not
themselves endpoint- or network-generated evidence.

## Publication boundary

Before any PCAP is committed, inspect it for unintended data.

The public evidence set must exclude:

- credentials or authorization headers;
- cookies or session material;
- personal information;
- unrelated host traffic;
- external service traffic not required by the scenario;
- sensitive filesystem or environment information.

A raw PCAP may be retained publicly only if review demonstrates that its contents
are limited to the intentionally generated laboratory sequence.

## Completion criteria

SOC-2026-005 may move from **PLANNED / PENDING EXECUTION** to
**REAL CONTROLLED LAB** only after:

1. the formal capture is completed;
2. source and derived artifacts are validated;
3. the packet capture is reviewed for publication safety;
4. findings are derived from retained evidence;
5. limitations and alternative explanations are documented;
6. repository validation passes for the exact candidate commit.
